UC-01 — Sign in to the system (worked example — delete)

Priority: Must Frequency: Several times a day, per user Requirements: FR-01, FR-02, NFR-03 Status: Approved

Description

A registered user proves who they are so the system can show them their own work and apply the permissions of their role. This is the entry point to almost every other use case, so it has to be quick for the person who remembers their password and forgiving for the person who does not.

Actors

  • Primary actor: Registered user — anyone with an active account.
  • Secondary actors: Email service, which delivers the reset link.
  • Systems involved: The company directory, which holds the account and its role.

Preconditions

  • The user has an account, and it is active rather than suspended or expired.
  • The user is not already signed in on this device.
  • The system can reach the company directory.

Postconditions

  • On success: the user has a session, sees the home page for their role, and the sign-in is recorded in the audit log with the time and the device.
  • On failure: no session is created, and the failed attempt is recorded against the account.

Main flow

  1. UserOpens the sign-in page.
  2. SystemShows fields for the email address and the password.
  3. UserEnters their email address and password, and confirms.
  4. SystemChecks the details against the company directory.
  5. SystemCreates a session and records the sign-in in the audit log.
  6. SystemOpens the home page for the user's role.

Alternative flows

UC-01-A1 — The user has forgotten their password

Branches from step 2. The user cannot remember their password.

  1. The user chooses “Forgotten your password?” and enters their email address.
  2. The system sends a reset link that expires after 30 minutes. It shows the same confirmation message whether or not the address belongs to an account, so the page cannot be used to discover who has one.
  3. The user opens the link and sets a new password.
  4. The system confirms the change, ends every other session for that account, and returns the user to step 2 of the main flow.
UC-01-A2 — The user's role requires a second factor

Branches from step 4, after the details are accepted. The account holds an administrative role.

  1. The system asks for the six-digit code from the user's authenticator app.
  2. The user enters the code.
  3. The system accepts it and continues from step 5 of the main flow.
  4. If the code is wrong three times in a row, the flow continues as UC-01-E2.
UC-01-E1 — The details are not correct

Branches from step 4. The email address or the password does not match.

  1. The system shows one message — “those details do not match” — without saying which of the two was wrong.
  2. The system records the failed attempt and returns the user to step 2.
UC-01-E2 — Too many failed attempts

Branches from UC-01-E1. Five failed attempts on the same account within 15 minutes.

  1. The system locks the account for 15 minutes and tells the user when they can try again.
  2. The system emails the account holder that this happened.
  3. The use case ends without a session.
UC-01-E3 — The company directory cannot be reached

Branches from step 4. The directory does not answer within five seconds.

  1. The system tells the user that sign-in is temporarily unavailable and asks them to try again shortly. It does not show the technical error.
  2. The system raises an alert to the support team.
  3. The use case ends without a session.

Notes

  • Business rule. A session ends after 12 hours, or after 30 minutes with no activity — whichever comes first (BR-01).
  • Deliberately excluded. Signing in with a Google or Microsoft account is out of scope for this release; see the out of scope table.
  • Open question. Should the lock in UC-01-E2 clear itself after 15 minutes, or wait for the support team to release it? Owner: the security team. Needed by <YYYY-MM-DD>.
  • Assumption. Every user has an email address the system can reach (A-01).

Before you publish

  • grep -n '&lt;[A-Z][A-Z0-9_]*&gt;' USECASE_SPECIFICATION.html returns nothing.
  • The comment block at the top of the file is deleted.
  • Every GUIDANCE, OPTIONAL and REQUIRED-IF box is deleted, along with any section it told you to remove — heading, box and body.
  • The worked example UC-01 is deleted, or replaced by a real use case of your own.
  • The overview ends with the positioning statement, and it reads well when quoted on its own.
  • Every goal has a number and a date.
  • Every stakeholder resolves to a real person or team with a working contact.
  • Every non-functional requirement has a measurable target and a stated way of checking it.
  • Every functional requirement appears in the traceability matrix, and every use case covers at least one requirement.
  • Every use case has at least one error flow, and states what happens when the actor cancels.
  • Every open question in a Notes section has an owner and a date.
  • Every term that a reader outside the team would not know is in the glossary.
  • Document control lists the author, the version, the status and the approvers, and the revision history has a row for this version.
  • No password, token, internal hostname or customer name appears anywhere in the document.
  • The document has been read once in a browser and once as a printed PDF.
  • Delete this checklist.
